## 🛡 Пентест боевого прода (2026-09-10) — критичная дыра закрыта

Владелец попросил боевой тест на устойчивость к атаке (цели: CRM не должна упасть, ПДн
не должны утечь). Провёл чёрный-бокс против живого `crm-nevarium.ru` + параллельно Codex
white-box аудит кода. Полностью — в git log, здесь суть.

**🔴 КРИТИЧНО, найдено и закрыто (`406955b`, задеплоено и проверено на проде):**
Обход авторизации через процентное кодирование пути. Хук авторизации сверял СЫРОЙ
`req.url` с `/api/crm/`, а роутер Fastify декодирует `%63→c` ДО подбора роута. Запрос
`GET /api/%63rm/contacts` не совпадал с префиксом → авторизация пропускалась → но роутер
вёл на настоящий CRM-обработчик. Итог: **любой в интернете без входа читал весь список
контактов/сделок/пользователей с ПДн** (имена, телефоны, email). Годилось любое кодирование
любой буквы. Фикс: матч по `req.routeOptions.url` (канонический шаблон роута, кодированием
не подделать) + fail-safe по раскодированному URL. Регресс-тест на 5 вариантов кодирования.
**Урок на будущее: НИКОГДА не завязывать авторизацию на строковый матч `req.url` — только
на `routeOptions.url` или на хук, привязанный к самим роутам.**

**🟡 Hardening (`f282893`):** добавлены заголовки безопасности (CSP, HSTS,
X-Content-Type-Options, X-Frame-Options, Referrer-Policy) через onRequest-хук. CSP подобран
под реальный фронт (Google Fonts разрешены явно, `script-src 'self'` без unsafe-inline),
проверен в браузере на собранном `dist/` — приложение работает, шрифтов CSP не ломает.

**✅ Держит удар (проверено, дыр нет):** SQL-инъекции (всё параметризовано), CSRF (сверка
Origin), bodyLimit (413 на >64КБ), кривой JSON (чистый 400 без стектрейса), перебор
пользователей (тайминг выровнен `fakeVerifyDelay`), троттлинг логина (раздельные хранилища
accounts/volatile, потолок памяти `MAX_BUCKETS`, душит параллель резервированием), хранимый
XSS (уведомления HTML-эскейпятся, фронт без `dangerouslySetInnerHTML`). **CRM под всеми
инъекциями/переполнениями осталась жива.**

**Codex white-box аудит (второе мнение) — 6 находок, проверены построчно:**

- **#5 (сделано, `2803761`):** у `/api/auth/login` не было своего `bodyLimit` (дефолт
  Fastify ~1 МБ) → занижен до 4 КБ; параллельные крупные тела больше не разбираются в
  память до троттлинга. Тест: >4 КБ → 413.
- **#6 (сделано, `2803761`):** обработчик ошибок отдавал наружу сырой текст непредвиденной
  5xx (мог раскрыть схему БД/инфраструктуру) → теперь обобщённый `{error:'internal'}` +
  детали в серверный лог; клиентские 4xx (битый JSON, тело велико) не тронуты.
- **#4 (сделано, `cdfa048`):** лимитеры `leadHits`/`hardHits` чистились по времени, но без
  потолка числа IP-ключей (спрей уникальных IP растил Map) → добавлен `MAX_IP_BUCKETS` с
  вытеснением только «холодных» записей, по образцу `auth.js`.

**Отложено осознанным решением владельца (2026-09-10) — не заплатки, а фичи/рефакторинги
с нулевой пользой сейчас и реальным риском регрессии на только что запущенном проде:**

- **#1 проектная авторизация (IDOR) — ОТЛОЖЕНО.** Любой залогиненный пользователь видит
  данные ВСЕХ проектов, не только своего (список без `project`, чужой `?project=`, любой
  `id`). **Сейчас не эксплуатируется:** пользователь один, админ; «участников» нет, а роль
  member и не задумана ограниченной по проекту. Это многопользовательская модель доступа
  (таблица `user_projects` + фильтрация ВСЕХ чтений/мутаций/дашборда + UI назначения
  проектов участнику). **Делать, когда впервые понадобится дать кому-то доступ с
  ограничением по проекту** — тогда же спроектировать UI и поведение по умолчанию
  (новый участник fail-closed: без назначений видит ничего).
- **#2 дедуп лидов в памяти — ОТЛОЖЕНО.** `findExistingContact` (app.js) на каждый

  потоковая выгрузка строк в JSON + потоковый multipart-upload.

## ✅ Перевод CRM на PostgreSQL (в `main`, коммит `9fe0649`)

**Зачем:** ADR-003 (SQLite на РФ-VPS) получил статус «заменено». Timeweb App Platform не
сохраняет файлы контейнера между деплоями — SQLite-файл терял бы все заявки при каждом
обновлении. План согласован владелицей отдельно: `nevarium-spb/nevarium-lab#3`,
ключевой документ — `docs/CRM_POSTGRES_MIGRATION_SPEC.md` в той ветке.

**Сделано целиком (этапы 1–6 плана):**
- `server/schema.sql` — одна цельная идемпотентная схема вместо массива миграций и
  `PRAGMA user_version`. Понятия «применить только недостающее» больше нет.
- `server/db-adapter.js` — асинхронный слой над `pg`, имитирующий интерфейс
  `.prepare(sql).get/all/run()` от better-sqlite3 (включая именованные `@col`-параметры),
  чтобы не переписывать текст SQL по всему `app.js`. Плюс `withTransaction`,
  `resyncIdentitySequence`, `tryClaimIdempotencyKey`.
- `server/app.js` — переведён целиком: auth, generic CRUD, дашборд, приём лидов/ПДн,
  анонимизация, экспорт/импорт, диагностика.
- **Идемпотентность публичного приёма переписана с check-then-act на claim-first.** Старая
  схема была безопасна только потому, что better-sqlite3 синхронный и между проверкой ключа
  и записью не было ни одного `await`. С `pg` это перестало быть верно.
- `telegram.js`, `bootstrap.js`, `backup.js`, `seed-admin.js`, `dev.js`, `index.js`.
  `backup.js` лишился `.sqlite`-копии: `VACUUM INTO` — SQLite-специфика без аналога в
  Postgres. Единственный формат бэкапа теперь JSON, его дополняют автобэкапы самой базы.
  (Позже, 2026-10-04, ночной бэкап в MAX удалён совсем — ADR-017; `backup.js` больше нет.)
- `DB_FILE` → `DATABASE_URL` везде, включая `deploy/`.
- Тесты — на `pg-mem` (эмулятор в памяти) вместо `:memory:` SQLite.

**Проверено:** `npm test` — 230 зелёных + 7 намеренно `it.skip`, всего 237. `npm run build`
проходит. Прогон на настоящем Postgres выполнен — см. раздел ниже.

### Ревью перевода (gstack `/review`: 6 специалистов + адверсариальный проход)

Security и data-migration — чисто. Остальные нашли **5 настоящих дефектов, все исправлены**:

1. **Воронка на дашборде молча потеряла «(+N без суммы)».** Алиас `noAmount` был
   неквотированным, а Postgres складывает такие идентификаторы в нижний регистр → ключ
   приходил как `noamount`, фронт читает `f.noAmount` и получал `undefined`. SQLite регистр
   сохранял. Починено квотированием; проверено эмпирически.
2. **Сид проектов перестал быть атомарным.** Вставка шла по одному проекту без транзакции,
   а условие входа — «проектов ноль». Падение между двумя INSERT → при следующем старте
   проектов уже не ноль, сид не выполнится никогда, «Невариум Визор» пропадает навсегда,
   его заявки молча уезжают в проект по умолчанию. Обёрнуто в `withTransaction`.
3. **Воркер outbox мог ронять весь процесс CRM.** Внешний `SELECT` стоял в `try/finally`
   без `catch`, а `tick()` вызывается из `setInterval` — отказ базы давал необработанное
   отклонение промиса, что в Node по умолчанию валит процесс. С файлом SQLite это почти не
   случалось; с управляемым Postgres рестарт базы при обслуживании — штатное событие.
4. **`deploy/README.md` вёл владелицу по нерабочему пути:** ставил `DB_FILE` (код его больше

переменная `TEST_DATABASE_URL` переключает весь набор тестов с `pg-mem` на живую базу


**Результат на PostgreSQL 16.15: 224 из 224 зелёных**, включая семь тестов, которые под `pg-mem` пропускаются.
Прогон повторён после правок пяти раундов ревью (четыре Codex + gstack /review, семь специалистов). На `pg-mem` —
230 зелёных + 7 пропущенных.

Один тест (`оживший прежний владелец откатывает заявку`) проверяет отсутствие дубля
только под `REAL_PG`: под `pg-mem` откат не исполняется, строки остаются.
Отдельно прогнаны 11 сценариев, которых в наборе нет (конкурентность, типы, счётчики) —
все прошли: `setval` действительно выполняется (предупреждений «пропущено» нет),
упавший импорт откатывается целиком и не понижает счётчики, `COUNT`/`SUM` приходят
числами, импорт под потоком из 40 заявок проходит и заявки после него сохраняются,
дамп, снятый под потоком из 60 заявок, не содержит сделок без контакта и импортируется
без ошибки внешнего ключа, дамп с воронкой возврата восстанавливается.

**Что это НЕ отменяет:** прогон был против PostgreSQL 16 в Docker, а не против
управляемой базы Timeweb. Версия, настройки и сеть там свои — повторить этот же
прогон на боевом `DATABASE_URL` перед первым деплоем всё ещё нужно, но теперь это
одна команда, а не список ручных шагов.

Ниже — что именно проверяется и почему `pg-mem` этого не закрывает в принципе.

- **Атомарность приёма запроса по ПДн** — третий `it.skip` («сбой на уведомлении не
  оставляет ни запроса, ни занятого ключа»). Сорвать `INSERT INTO outbox` на живой базе:
  после отказа в `pd_requests` и `idempotency_keys` не должно остаться ничего, а повтор
  с тем же `Idempotency-Key` обязан создать РОВНО ОДИН запрос. Под `pg-mem` непроверяемо
  по той же причине, что и откат импорта ниже.
- **Атомарность отката импорта** — два `it.skip`-теста (битый файл, чужеродная колонка).
  После отклонённого импорта старые данные обязаны остаться на месте. `pg-mem` не даёт
  реальной изоляции: вставка внутри откаченной транзакции у него остаётся закоммиченной.
- **`resyncIdentitySequence`** — под `pg-mem` пишет в лог «пропущено —
  pg_get_serial_sequence недоступна» (5 мест) и **никогда не выполняет свой `setval`**. Под
  настоящим Postgres этих строк быть не должно. Проверка по существу: импортировать дамп,
  затем создать новый контакт руками — оба должны сосуществовать без ошибки PRIMARY KEY.
  Отдельно проверить УПАВШИЙ импорт (дамп с чужеродной колонкой в поздней таблице): после
  отказа создание нового контакта тоже обязано работать. `setval` нетранзакционен, и
  раньше упавший импорт оставлял счётчики пониженными — теперь вызов вынесен в конец и
  двигает только вверх (`GREATEST`), но подтвердить это можно лишь на живой базе.
- **Блокировка таблиц на импорте** (`lockTablesForRestore`) — `pg-mem` не разбирает
  `LOCK TABLE` вовсе, автотест проверяет лишь текст и позицию команды. По существу:
  запустить импорт и одновременно слать заявки на `/api/leads` — заявки обязаны
  подождать конца восстановления и пройти после него, а не упасть на PRIMARY KEY.
- **Ограждение аренды ключа идемпотентности** — перезахват заводит НОВУЮ строку, и
  оживший прежний владелец обязан откатиться. Под `pg-mem` виден только сам факт
  отката (ROLLBACK вместо COMMIT), но не его результат. По существу: убедиться, что
  после отката второго запроса по ПДн в базе нет.
- **Согласованность JSON-бэкапа** (`withReadSnapshot`) — дамп читает семь таблиц в одной
  транзакции `REPEATABLE READ READ ONLY`. `pg-mem` уровень изоляции разбирает, но не
  соблюдает, поэтому автотест проверяет лишь сам факт запроса снимка. По существу: снять
  бэкап, пока в другом окне идёт поток заявок, затем импортировать полученный файл —
  он обязан пройти без ошибки внешнего ключа.
- **`pg.types.setTypeParser(20, parseInt)`** (`server/db.js`) — лечит BIGINT-как-строку от
  `COUNT()`/`SUM()`. `pg-mem` отдаёт числа нативно, поэтому тесты зелены и **без** этой
  строки: регрессия здесь автотестами не ловится вообще. Проверка: открыть дашборд и
  убедиться, что счётчики и суммы воронки — числа, а не строки.
- **Импорт дампа с воронкой возврата** — FK-порядок `tasks → winback_sequences → deals`.

### Ограничения `pg-mem`, не относящиеся к реальному Postgres

Держать в голове: это движок тестов, а не СУБД. Всё найдено изолированной репродукцией;
где обходной путь валиден и для настоящего Postgres — применён в коде.

1. `BEGIN/COMMIT/ROLLBACK` парсятся, но не дают реальной изоляции (см. чек-лист выше).
2. `INSERT ... ON CONFLICT DO NOTHING RETURNING` при конфликте возвращает существующую
   строку вместо пустого набора — поэтому захват ключа сделан через простой `INSERT` +
   `catch` на `23505`.
3. `pg_get_serial_sequence()` не реализована вовсе.
4. Повторный `CREATE TABLE IF NOT EXISTS` на уже применённой схеме падает внутренней
   ошибкой — не мешает, т.к. каждый тест поднимает свой инстанс.
5. `stage NOT IN (...)` на индексированной колонке падает внутри `BIndex.nin`. Обход:
   `NOT (stage IN (...))` — семантически то же самое.
6. Коррелированный `NOT EXISTS`/скалярный подзапрос вместе с `GROUP BY` по колонке из
   JOIN даёт ложное «column "c.id" does not exist». Обход: агрегация вынесена в
   некоррелированную производную таблицу.
7. Возвращает `COUNT`/`SUM` числами, а не строками, маскируя необходимость `setTypeParser`.

## Как запустить

```bash
npm install
# DATABASE_URL обязателен: файла-базы «из коробки», как было у SQLite, больше нет
DATABASE_URL=postgresql://user:pass@localhost:5432/nevarium_crm node server/dev.js  # :3001
npm run dev     # :5173 → открыть / (перекинет на /crm)
npm test        # Postgres НЕ нужен: тесты поднимают pg-mem на каждый тест
```
Первый админ: `npm run seed-admin` (интерактивно) или `BOOTSTRAP_ADMIN_*` при первом старте.
