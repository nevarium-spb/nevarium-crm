# Развёртывание: Невариум CRM на Timeweb Cloud

Хостинг — **Timeweb Cloud** (ADR-004 в `docs/DECISIONS.md`). Один образ (`deploy/Dockerfile`)
содержит и API, и собранный фронт CRM — Node сам отдаёт статику (ADR-008), отдельный
контейнер с Caddy не нужен. Маркетинговые сайты (nevarium1, nevarium_vizor) — отдельные
проекты, хостятся отдельно (Vercel), сюда только шлют заявки через `POST /api/leads`.

## Что нужно от вас (один раз)

1. **Аккаунт Timeweb Cloud** — создать самостоятельно (я не создаю аккаунты за вас), timeweb.cloud.
2. **Домен CRM: `crm-nevarium.ru`** — куплен в Ru-Center (nic.ru), оплачен до 27.07.2027.
   Сейчас делегирован на статусную страницу Ru-Center — при развёртывании переключить
   DNS на адрес, который выдаст Timeweb (см. шаг 5). Отдельный домен, а не поддомен
   любого из сайтов: CRM обслуживает оба бизнеса.
3. **Сервер в Timeweb** — см. «Вариант A» ниже (рекомендуется) или «Вариант Б».
4. **Telegram-бот**: напишите @BotFather → `/newbot` → получите токен. Добавьте бота
   в рабочую группу. Узнайте chat_id группы: перешлите её сообщение боту @getmyid_bot
   (покажет id вида `-100…`).
4а. **Бот в MAX (необязательно, второй канал уведомлений параллельно с Telegram)**:
    заведите бота через MAX для бизнеса (dev.max.ru — нужна верификация организации/ИП),
    получите токен и chat_id. Если не завести — уведомления просто продолжат идти
    только в Telegram, ничего не сломается.
5. **DNS**: у `crm-nevarium.ru` в Ru-Center переключить со статусной страницы на адрес сервера.
6. **База данных: Managed PostgreSQL в Timeweb** (перевод на Postgres, план в
   `nevarium-spb/nevarium-lab#3`; раньше данные лежали в файле SQLite внутри контейнера —
   App Platform не сохраняет файлы контейнера между деплоями, и каждое обновление стирало бы
   все заявки). В панели Timeweb: **Базы данных → Создать → PostgreSQL**, регион тот же, что
   у приложения (Москва/СПб — 152-ФЗ), минимальная конфигурация. Оттуда возьмите строку
   подключения вида `postgresql://user:pass@host:5432/dbname?sslmode=require` — это
   `DATABASE_URL` для шага 7 «Варианта А». **Включите автоматические бэкапы базы** в её
   настройках — это единственный автоматический бэкап базы (ночного бэкапа в самом
   приложении нет, ADR-017). Ручной «Экспорт JSON» в настройках CRM — дополнительная копия; где её хранить
   (в т.ч. вне Timeweb) — ожидает решения владельца, см. ADR-017.

## Вариант А — App Platform (рекомендуется)

Цена почти не отличается от голого VPS (проверено 2026-07-28: 510 ₽/мес против 450 ₽/мес
за 1 vCPU/1 ГБ/15 ГБ NVMe в Москве) — 60 ₽/мес за то, что Timeweb сам ставит Docker,
обновляет по git-пушу и выдаёт SSL. Голый VPS — Вариант Б ниже — держим на случай,
если однажды понадобится больше контроля.

1. В панели Timeweb: **App Platform → Добавить App**.
2. Тип: **Docker → Dockerfile** (не Docker Compose — он был для Варианта Б, теперь не нужен).
3. Репозиторий: подключите GitHub, выберите `nevarium-spb/nevarium-crm` (приватный —
   дайте приложению Timeweb доступ именно к этому репозиторию).
4. Путь к Dockerfile: `deploy/Dockerfile` (само приложение собирается из корня репозитория —
   `COPY . .` внутри Dockerfile ожидает корень, отдельно указывать build-context не нужно).
5. Регион: Москва (или Санкт-Петербург) — важно, чтобы сервер физически был в РФ (152-ФЗ).
6. Конфигурация: минимальная (1 vCPU / 1 ГБ RAM / 15 ГБ NVMe) — этого достаточно.
7. **Переменные окружения** (вводятся в интерфейсе Timeweb, не файлом `.env` — на
   App Platform нет shell-доступа для его ручного создания):
   ```
   JWT_SECRET=<сгенерировать: openssl rand -hex 32, или любые 32+ случайных символа>
   TG_BOT_TOKEN=<токен из шага 4>
   TG_CHAT_ID=<chat_id из шага 4>
   MAX_BOT_TOKEN=<токен бота MAX, если завели — необязательно>
   MAX_CHAT_ID=<chat_id в MAX, если завели — необязательно>
   CRM_BASE_URL=https://crm-nevarium.ru
   APP_ORIGIN=https://crm-nevarium.ru
   DATABASE_URL=<строка подключения к Managed PostgreSQL из панели Timeweb>
   PORT=3001

   # Почта для СЛУЖЕБНЫХ писем сотрудникам (восстановление пароля, смена email) — необязательно.
   # Не настроено — «Забыли пароль?» честно пишет, что недоступно; пароль сбрасывается командой
   # npm run reset-admin (см. ниже). Gmail: пароль приложения Google, не пароль от аккаунта.
   SMTP_HOST=smtp.gmail.com
   SMTP_PORT=465
   SMTP_USER=amakejev@gmail.com
   SMTP_PASS=<пароль приложения Google>
   SMTP_FROM=amakejev@gmail.com

   # Только для самого первого запуска — создаст первого администратора
   # автоматически (bootstrap.js), поскольку зайти в контейнер по shell нельзя.
   BOOTSTRAP_ADMIN_EMAIL=<ваша почта>
   BOOTSTRAP_ADMIN_PASSWORD=<пароль, минимум 12 символов, не из списка частых>
   BOOTSTRAP_ADMIN_NAME=<ваше имя>
   ```
8. **Постоянное хранилище**: данные живут в Managed PostgreSQL (шаг 6 выше), ОТДЕЛЬНО от
   контейнера приложения — именно ради этого делался перевод с SQLite. Эфемерность диска
   контейнера теперь безразлична. **Всё равно проверьте на практике после первого деплоя**:
   сделайте тестовую заявку, затем запустите передеплой (например, пустой коммит) и
   убедитесь, что заявка на месте. Если пропала — значит приложение подключилось не к той
   базе (проверьте `DATABASE_URL`), а не «диск не персистентный».
9. Заказать. После первого успешного запуска — **снимите переменные `BOOTSTRAP_ADMIN_*`**
   из настроек приложения (пароль в них больше не нужен, а держать его там незачем).
10. Зайдите на выданный Timeweb адрес → `/crm` → войдите тем логином, что указали
    в `BOOTSTRAP_ADMIN_EMAIL`.

Домены сайтов, заявки и приём лидов — см. общий раздел «Проверка» ниже.

### Почта и восстановление пароля (ADR-020)

- Почта — **только служебные письма сотрудникам CRM** (ссылка восстановления, подтверждение
  нового email, уведомление о смене пароля). Никаких писем клиентам и никаких данных клиентов
  через неё: Gmail — зарубежный сервис, а политика ПДн обещает клиентам, что их данные не
  покидают Россию. Менять это нельзя без правки политики.
- Переменные `SMTP_*` (выше) задаются **только в настройках приложения Timeweb** — не в репозитории
  и не в логах. «Пароль приложения» создаётся в аккаунте Google (двухэтапная проверка → «Пароли
  приложений»); обычный пароль от почты не подойдёт. Ссылки в письмах строятся от `CRM_BASE_URL`.
- Проверка: на экране входа «Забыли пароль?» → ваш email → письмо должно прийти за минуту.
  Письма нет — проверьте папку «Спам» и логи приложения (в них только причина сбоя, без пароля и адреса).

### Хостинг режет SMTP → отправка через Yandex Cloud Postbox (`POSTBOX_*`)

На Timeweb App Platform исходящий SMTP закрыт целиком (проверено 2026-10-17: таймаут на портах 465/587/2525
у Gmail, mail.ru, Яндекса и самого Timeweb; HTTPS наружу работает). Поэтому письма уходят через HTTPS-API
Yandex Cloud Postbox (первые 2000 писем в месяц бесплатно, дальше от 80 ₽ за 1000; нашим целям хватит с огромным запасом):

1. В консоли Yandex Cloud (нужен платёжный аккаунт, списаний в пределах бесплатных 2000 писем нет) открыть
   Postbox → создать адрес для домена `crm-nevarium.ru`, сгенерировать ключ DKIM и внести показанную TXT-запись
   в DNS у регистратора; дождаться статуса «подтверждён».
2. Создать сервисный аккаунт с ролью `postbox.sender` и **статический ключ доступа** (идентификатор и секрет;
   секрет показывается один раз).
3. В настройках приложения Timeweb задать `POSTBOX_KEY_ID`, `POSTBOX_SECRET_KEY` и
   `SMTP_FROM=<адрес на этом домене, например crm@crm-nevarium.ru>`. Переменные `SMTP_HOST/USER/PASS`
   убрать (при заданных ключах Postbox они не используются). Перезапустить приложение.
4. Проверить командой `npm run test-mail` (ниже). Письма — только простой текст, без html и без подмены ссылок.

### Письмо не приходит? `npm run test-mail`

В консоли приложения на Timeweb выполните `npm run test-mail`: команда покажет настройки почты (пароль и ключ не
показываются — только «задан» и длина), для SMTP проверит, доходит ли сервер до порта, и отправит одно тестовое
письмо сотруднику CRM (по умолчанию — первому администратору; на вопрос «Кому» достаточно нажать Enter — адрес
должен быть адресом сотрудника из CRM, иначе ничего не отправится). При ошибке выведет точный ответ и подсказку:
для SMTP — неверный «пароль приложения», пробелы в пароле или блокировка порта хостингом; для Postbox — неверный
ключ, нет роли `postbox.sender` или неподтверждённый домен отправителя.
Те же причины пишутся и в лог приложения строками `forgot:` и `mail …:`.

### Уведомления о заявках в MAX и Telegram: `npm run test-notify`

В уведомлениях нет персональных данных (ADR-018): проект, источник, ссылка на карточку, тариф и число фото. Каналы включаются
переменными приложения Timeweb: MAX — `MAX_BOT_TOKEN` и `MAX_CHAT_ID`, Telegram — `TG_BOT_TOKEN` и `TG_CHAT_ID`; в «Настройках»
CRM каждый канал можно отдельно включить и выключить.

В консоли приложения: `npm run test-notify max` (или `tg`, или без слова — оба канала). Команда по шагам проверяет: настройки →
токен бота принят → чат найден и активен → тестовое сообщение дошло (оно без персональных данных; придёт в сам чат). На каждом
шаге пишет, что не так и что поправить. Токены не печатаются — только «задан» и длина. Если уведомление не дошло при настоящей
заявке, точный отказ сервиса теперь виден в «Логах приложения» строкой `outbox[max]: … не удалась: Error: MAX HTTP …: <причина>`.

**MAX.** Токен выдаётся при создании бота в кабинете MAX; бота нужно **добавить в чат или канал** (в канале — администратором с
правом писать), `MAX_CHAT_ID` — числовой идентификатор этого чата, он может быть отрицательным. **Ссылка на бота или чат
(`https://max.ru/…`) в `MAX_CHAT_ID` не годится** — MAX ответит 400. Если бота из чата убрали или чат закрыли, `test-notify`
покажет статус «removed/left/closed» — тогда создайте чат заново и обновите `MAX_CHAT_ID`.

Как найти `chat_id` (список чатов у MAX отключён, идентификатор берётся из событий бота): откройте бота в MAX, нажмите «Начать»
и напишите ему любое слово — это личный чат с ботом, самый простой вариант (в группах и каналах боту нужны права
администратора, а группы у непроверенных ботов могут быть закрыты в настройках приватности). Сразу после этого в консоли
приложения: `npm run test-notify max ids` — команда напечатает `chat_id` (текст сообщений она не читает). Это число — в
`MAX_CHAT_ID`, перезапуск, затем `npm run test-notify max`. События бота хранятся недолго — запускайте команду сразу.

**Telegram.** Бота создаёт @BotFather (`/newbot` → имя и username, заканчивающийся на `bot`) и выдаёт токен вида `123456:ABC…` —
это `TG_BOT_TOKEN`. Откройте своего бота в Telegram, нажмите «Start» и напишите ему любое слово (или добавьте бота в группу и
напишите там). Затем в консоли приложения: `npm run test-notify tg ids` — команда напечатает `chat_id` (для группы он
отрицательный; текст сообщений и имена она не читает и не печатает). Это число — в `TG_CHAT_ID`, перезапуск приложения, затем
`npm run test-notify tg`. Если бот когда-то был подключён к вебхуку, Telegram событий не отдаёт. Сообщения без персональных
данных (ADR-018, ADR-009).

### Фото из заявок сайта Визора — хранилище S3 Timeweb (ADR-022)

Фото приходят как есть, вместе с EXIF (в нём бывают координаты съёмки, то есть адрес объекта), поэтому хранятся
в **приватном** бакете S3 Timeweb, а не на диске контейнера (диск стирается при каждом деплое) и не в базе.

1. Хранилище S3 в панели Timeweb: тариф «Стандартный», 1 ГБ (1 ₽ в месяц), **автомасштабирование включено**, тип бакета —
   **«Приватный»**. Для заявок с фото в среднем 20 МБ хватает примерно на 50 штук; на странице «Настройки» CRM виден счётчик
   занятого места и предупреждение с 80%.
2. Переменные приложения Timeweb (значения — из панели хранилища, секрет в чат не слать): `S3_ENDPOINT=https://s3.twcstorage.ru`,
   `S3_BUCKET=nevarium-crm-photo`, `S3_REGION=ru-1`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`; необязательно `PHOTO_STORAGE_LIMIT_MB`
   (лимит тарифа в МБ для счётчика, по умолчанию 1024 — при росте тарифа обновить). Перезапустить приложение.
3. Проверка в консоли приложения: `npm run test-s3` — записывает, читает и удаляет служебный файл; должно быть «OK» трижды.
4. Предел тела запроса на App Platform проверить на практике (сайт шлёт файлы до 15 МБ, маршрут принимает до 16 МБ): если
   платформа режет меньше, сообщить сессии сайта новый лимит.
5. Когда всё работает — сообщить сессии сайта «приём фото готов» (сайт соберут с `VITE_LEAD_PHOTOS=1`).

Резервные копии: фото в «Физические бэкапы» базы не входят и в экспорт JSON не входят; импорт JSON удаляет все фото (id
контактов после восстановления другие). Если хранилище переполнено или недоступно, заявки принимаются как обычно, а фото
к ним не прикрепляются (сайт получает 503 и повторяет).

### Фото и видео этапа по личной ссылке, отчёты в кабинете, письма клиенту (ADR-025)

Тот же приватный бакет. Видео (до 300 МБ) телефон клиента загружает прямо в бакет по подписанной форме — мимо лимита тела хостинга.

1. В консоли приложения: `npm run test-s3`. Кроме записи/чтения/удаления, теперь проверяется загрузка по подписанной форме и то,
   что файл больше лимита из подписи отклоняется — все шаги должны быть «OK». Не прошла «загрузка по подписанной форме» — видео
   напрямую в бакет не работает: показать вывод, обратиться в поддержку Timeweb (POST policy).
2. `npm run test-s3 cors apply` — выставить бакету правило CORS: только метод POST и только домены сайта
   (`https://nevarium-vizor.ru`, `https://www.nevarium-vizor.ru`; другие — переменной `S3_CORS_ORIGINS` через запятую). Команда
   ЗАМЕНЯЕТ правила целиком; `npm run test-s3 cors` — только показать текущие.
3. Сессии сайта: видео грузится на `https://s3.twcstorage.ru/nevarium-crm-photo`, в CSP `connect-src` — `https://s3.twcstorage.ru`.
4. Письма клиенту («Отчёт готов», «Пришлите фото этапа») — **выключены** до подтверждения сайта, что новая политика ПДн выложена;
   включаются в «Настройках» CRM («Письма клиентам»). Отправитель — тот же `SMTP_FROM` (Postbox) с именем «Невариум Визор», ответ на
   `nvizor-spb@yandex.ru`; переопределить — `CLIENT_MAIL_FROM_NAME`, `CLIENT_MAIL_REPLY_TO`. Памятка «как снимать» в письме о фото
   этапа — по умолчанию `https://nevarium-vizor.ru/photo-guide`; другая — `CLIENT_GUIDE_URL`, пустое значение убирает фразу.

### Запасной путь: сбросить пароль из консоли (`npm run reset-admin`)

Если почта недоступна и вы забыли пароль (вы — единственный администратор): откройте консоль
приложения на Timeweb и выполните

```
npm run reset-admin
```

Скрипт спросит email и новый пароль (дважды; при вводе пароль не отображается). Пароль нельзя
передавать аргументом команды — он осел бы в истории оболочки. Правила те же, что в «Настройках»:
от 12 символов, не из списка частых. Скрипт сбрасывает **все** сессии, гасит висящие ссылки из
писем и пишет в журнал действий (без пароля) запись от имени «console».

### Запасной путь: сменить email входа из консоли (`npm run change-email`)

Смена email в «Настройках» требует письма с подтверждением на новый адрес. Пока почта не работает, поменять
email можно из консоли приложения на Timeweb: `npm run change-email` спросит текущий и новый адреса (пароль
не нужен и не меняется). Команда завершает **все** сессии пользователя (войдите заново прежним паролем), гасит
висящие ссылки из писем и пишет в журнал действий запись от имени «console». Занятый другой учётной записью
или некорректный адрес отклоняется, ничего не меняя.

## Вариант Б — голый VPS (запасной путь)

Держим на случай, если решите отказаться от App Platform. Использует
`deploy/docker-compose.yml` + `deploy/Caddyfile` — тот же образ приложения, что и в
Варианте А (фронт отдаёт сам Node), Caddy здесь только для HTTPS и явного управления
по SSH — он просто пробрасывает весь трафик на `app:3001`, статику не раздаёт.

```bash
git clone https://github.com/nevarium-spb/nevarium-crm.git && cd nevarium-crm

# 1. Секреты
cp deploy/.env.example deploy/.env
nano deploy/.env          # JWT_SECRET (openssl rand -hex 32), TG_BOT_TOKEN, TG_CHAT_ID, MAX_BOT_TOKEN/MAX_CHAT_ID (необязательно)

# 2. Домен
nano deploy/Caddyfile     # замените example.ru на ваш домен CRM

# 3. Запуск (образ теперь сам собирает и отдаёт фронт — отдельная сборка dist/ не нужна)
cd deploy && docker compose up -d --build

# 4. Первый администратор — интерактивно (пароль не остаётся в файлах)
docker compose exec app node server/seed-admin.js
```

> **Docker Hub из РФ**: если `docker compose build` не может скачать образы, раскомментируйте

## Проверка (оба варианта)

Домены обоих сайтов уже прописаны миграциями — `nevarium-lab.ru`, `nevarium-vizor.ru`
(каждый с www), плюс `nevarium1.vercel.app`. Отдельных действий не требуется. Если
понадобится добавить ещё один (например, превью-домен) — через страницу «Настройки»
в CRM или напрямую в БД (см. `docs/DECISIONS.md`, ADR-006): без домена в списке браузер
заблокирует отправку формы (CORS), заявка не дойдёт.

Проверьте, что вход в саму CRM работает: попробуйте создать или изменить контакт.
Если `APP_ORIGIN` указан неверно (опечатка, лишний слеш на конце, http вместо https) —
любое изменение будет падать с `403 forbidden`, хотя чтение (списки, дашборд) продолжит
работать. Это ожидаемо: значение должно точь-в-точь совпадать с тем, что браузер
присылает в заголовке `Origin` — то есть `https://crm-nevarium.ru`, без пути и слеша.

Откройте `https://ваш-домен/crm` → войдите → дашборд. Отправьте тестовую заявку с
сайта — она должна появиться в «Новых лидах», и придут два уведомления (ADR-009):
в **Telegram** обезличенное, только проект, источник и ссылка на карточку; в **MAX**
полное, с именем, контактом и задачей. Так и задумано: MAX российский, туда ПДн можно,
Telegram зарубежный — туда нельзя (152-ФЗ). Если в Telegram пришло имя или телефон —
это ошибка, не выкатывайте дальше.

## Бэкапы

Защита двухуровневая, и уровни разного рода:

| Что | Кто делает | Чем возвращается |
|---|---|---|
| Снимок всей базы | **Timeweb Managed PostgreSQL**, автобэкапы (включить в настройках базы, шаг 6) | из панели Timeweb, штатным восстановлением базы |
| `crm-ГГГГ-ММ-ДД.json` | наш сервер, каждую ночь в 04:00 МСК, отправка в **MAX** | «Импорт JSON» в настройках CRM, через браузер |

JSON-дамп уходит только в MAX и никогда в Telegram: внутри ПДн всех клиентов, а
Telegram зарубежный (152-ФЗ, ADR-009). В Telegram приходит лишь обезличенный статус,
если бэкап не отправился. На диске держатся 7 последних дат.

> **Почему не файл базы.** Раньше рядом с JSON уезжала вторая копия `.sqlite`
> (`VACUUM INTO`). С переводом на Postgres она исчезла: у Postgres нет такого
> однокомандного самодостаточного снимка (`pg_dump` в контейнере приложения может
> не быть), а роль «точной копии» теперь играют автобэкапы самой Timeweb-базы.
> JSON остаётся тем, чем и был: переносимым путём восстановления через браузер,
> единственным, который работает там, где нет shell (ADR-013).

### Восстановление на App Platform (основной путь, проверено)

1. Откройте `https://crm-nevarium.ru/crm`. Если база пуста и войти не под кем —
   временно верните переменные `BOOTSTRAP_ADMIN_*` в настройках приложения,
   передеплойте, войдите, потом снимите их обратно.
2. Скачайте из чата с ботом MAX последний файл `crm-ГГГГ-ММ-ДД.json`.
3. В CRM: **Настройки → Импорт JSON** → выберите скачанный файл.
   Импорт **заменяет все данные целиком** и спрашивает подтверждение дважды.
4. Проверьте дашборд: контакты, сделки, воронка, раздел «Права ПДн».

### Восстановление из снимка базы (точный путь)

Восстановление автобэкапа Managed PostgreSQL делается в панели Timeweb, средствами
самой базы — приложение при этом трогать не нужно, оно подхватит восстановленные
данные по той же `DATABASE_URL`. Этот путь точнее JSON: возвращает в том числе
пользователей и серии воронки возврата, которых в дампе нет (см. ниже).

### Что JSON НЕ возвращает (важно знать заранее)

- **Пользователей и пароли.** После восстановления входите текущим админом или
  создайте его через `BOOTSTRAP_ADMIN_*`. Сделано намеренно: иначе чужой дамп мог бы
  подменить администратора и запереть вход.
- **Серии воронки возврата.** Задачи из них останутся с прежними заголовками и
  датами, но перестанут сниматься автоматически при возврате сделки в работу.
  Стадия «Проиграно» у сделки сохраняется, так что смысл не теряется.
- **Демо-данные.** В бэкап они не попадают вообще. Если тестируете на демо-базе,
  дамп будет выглядеть пустым — это правильное поведение, а не поломка.

Возвращается всё остальное, включая **запросы по персональным данным и журнал
действий** — то, чем доказывают Роскомнадзору исполнение обязательств в срок.

Ручной экспорт в любой момент: **Настройки → Экспорт JSON**.

```bash
# терминал 1: API (dev-режим, cookie без Secure).

```
