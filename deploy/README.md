# Развёртывание: Невариум CRM на Timeweb Cloud

Хостинг — **Timeweb Cloud** (ADR-004 в `docs/DECISIONS.md`). Один образ (`deploy/Dockerfile`)
содержит и API, и собранный фронт CRM — Node сам отдаёт статику (ADR-008), отдельный
контейнер с Caddy не нужен. Маркетинговые сайты (nevarium1, nevarium_vizor) — отдельные
проекты, хостятся отдельно (Vercel), сюда только шлют заявки через `POST /api/leads`.

## Что нужно от вас (один раз)

1. **Аккаунт Timeweb Cloud** — создать самостоятельно (я не создаю аккаунты за вас), timeweb.cloud.
2. **Домен CRM: `crm-nevarium.ru`** — куплен в Ru-Center (nic.ru), оплачен до 27.07.2027.
   Сейчас делегирован на статусную страницу Ru-Center — при развёртывании переключить
   DNS на адрес, который выдаст Timeweb (см. шаг 5). Отдельный домен, а не поддомен
   любого из сайтов: CRM обслуживает оба бизнеса.
3. **Сервер в Timeweb** — см. «Вариант A» ниже (рекомендуется) или «Вариант Б».
4. **Telegram-бот**: напишите @BotFather → `/newbot` → получите токен. Добавьте бота
   в рабочую группу. Узнайте chat_id группы: перешлите её сообщение боту @getmyid_bot
   (покажет id вида `-100…`).
4а. **Бот в MAX (необязательно, второй канал уведомлений параллельно с Telegram)**:
    заведите бота через MAX для бизнеса (dev.max.ru — нужна верификация организации/ИП),
    получите токен и chat_id. Если не завести — уведомления просто продолжат идти
    только в Telegram, ничего не сломается.
5. **DNS**: у `crm-nevarium.ru` в Ru-Center переключить со статусной страницы на адрес сервера.
6. **База данных: Managed PostgreSQL в Timeweb** (перевод на Postgres, план в
   `nevarium-spb/nevarium-lab#3`; раньше данные лежали в файле SQLite внутри контейнера —
   App Platform не сохраняет файлы контейнера между деплоями, и каждое обновление стирало бы
   все заявки). В панели Timeweb: **Базы данных → Создать → PostgreSQL**, регион тот же, что
   у приложения (Москва/СПб — 152-ФЗ), минимальная конфигурация. Оттуда возьмите строку
   подключения вида `postgresql://user:pass@host:5432/dbname?sslmode=require` — это
   `DATABASE_URL` для шага 7 «Варианта А». **Включите автоматические бэкапы базы** в её
   настройках: ночной JSON-дамп в MAX (`server/backup.js`) их дополняет, но не заменяет.

## Вариант А — App Platform (рекомендуется)

Цена почти не отличается от голого VPS (проверено 2026-07-28: 510 ₽/мес против 450 ₽/мес
за 1 vCPU/1 ГБ/15 ГБ NVMe в Москве) — 60 ₽/мес за то, что Timeweb сам ставит Docker,
обновляет по git-пушу и выдаёт SSL. Голый VPS — Вариант Б ниже — держим на случай,
если однажды понадобится больше контроля.

1. В панели Timeweb: **App Platform → Добавить App**.
2. Тип: **Docker → Dockerfile** (не Docker Compose — он был для Варианта Б, теперь не нужен).
3. Репозиторий: подключите GitHub, выберите `nevarium-spb/nevarium-crm` (приватный —
   дайте приложению Timeweb доступ именно к этому репозиторию).
4. Путь к Dockerfile: `deploy/Dockerfile` (само приложение собирается из корня репозитория —
   `COPY . .` внутри Dockerfile ожидает корень, отдельно указывать build-context не нужно).
5. Регион: Москва (или Санкт-Петербург) — важно, чтобы сервер физически был в РФ (152-ФЗ).
6. Конфигурация: минимальная (1 vCPU / 1 ГБ RAM / 15 ГБ NVMe) — этого достаточно.
7. **Переменные окружения** (вводятся в интерфейсе Timeweb, не файлом `.env` — на
   App Platform нет shell-доступа для его ручного создания):
   ```
   JWT_SECRET=<сгенерировать: openssl rand -hex 32, или любые 32+ случайных символа>
   TG_BOT_TOKEN=<токен из шага 4>
   TG_CHAT_ID=<chat_id из шага 4>
   MAX_BOT_TOKEN=<токен бота MAX, если завели — необязательно>
   MAX_CHAT_ID=<chat_id в MAX, если завели — необязательно>
   CRM_BASE_URL=https://crm-nevarium.ru
   APP_ORIGIN=https://crm-nevarium.ru
   DATABASE_URL=<строка подключения к Managed PostgreSQL из панели Timeweb>
   PORT=3001

   # Только для самого первого запуска — создаст первого администратора
   # автоматически (bootstrap.js), поскольку зайти в контейнер по shell нельзя.
   BOOTSTRAP_ADMIN_EMAIL=<ваша почта>
   BOOTSTRAP_ADMIN_PASSWORD=<пароль, минимум 16 символов>
   BOOTSTRAP_ADMIN_NAME=<ваше имя>
   ```
8. **Постоянное хранилище**: данные живут в Managed PostgreSQL (шаг 6 выше), ОТДЕЛЬНО от
   контейнера приложения — именно ради этого делался перевод с SQLite. Эфемерность диска
   контейнера теперь безразлична. **Всё равно проверьте на практике после первого деплоя**:
   сделайте тестовую заявку, затем запустите передеплой (например, пустой коммит) и
   убедитесь, что заявка на месте. Если пропала — значит приложение подключилось не к той
   базе (проверьте `DATABASE_URL`), а не «диск не персистентный».
9. Заказать. После первого успешного запуска — **снимите переменные `BOOTSTRAP_ADMIN_*`**
   из настроек приложения (пароль в них больше не нужен, а держать его там незачем).
10. Зайдите на выданный Timeweb адрес → `/crm` → войдите тем логином, что указали
    в `BOOTSTRAP_ADMIN_EMAIL`.

Домены сайтов, заявки и приём лидов — см. общий раздел «Проверка» ниже.

## Вариант Б — голый VPS (запасной путь)

Держим на случай, если решите отказаться от App Platform. Использует
`deploy/docker-compose.yml` + `deploy/Caddyfile` — тот же образ приложения, что и в
Варианте А (фронт отдаёт сам Node), Caddy здесь только для HTTPS и явного управления
по SSH — он просто пробрасывает весь трафик на `app:3001`, статику не раздаёт.

```bash
git clone https://github.com/nevarium-spb/nevarium-crm.git && cd nevarium-crm

# 1. Секреты
cp deploy/.env.example deploy/.env
nano deploy/.env          # JWT_SECRET (openssl rand -hex 32), TG_BOT_TOKEN, TG_CHAT_ID, MAX_BOT_TOKEN/MAX_CHAT_ID (необязательно)

# 2. Домен
nano deploy/Caddyfile     # замените example.ru на ваш домен CRM

# 3. Запуск (образ теперь сам собирает и отдаёт фронт — отдельная сборка dist/ не нужна)
cd deploy && docker compose up -d --build

# 4. Первый администратор — интерактивно (пароль не остаётся в файлах)
docker compose exec app node server/seed-admin.js
```

> **Docker Hub из РФ**: если `docker compose build` не может скачать образы, раскомментируйте
> зеркало в `deploy/Dockerfile` (mirror.gcr.io) или настройте registry-mirror в
> `/etc/docker/daemon.json` (huecker.io, dockerhub.timeweb.cloud).

### Обновление (Вариант Б)

```bash
git pull
cd deploy && docker compose up -d --build
```

### Откат (Вариант Б)

```bash
git checkout <прошлый-коммит> && # пересборка как выше
```

## Проверка (оба варианта)

Домены обоих сайтов уже прописаны миграциями — `nevarium-lab.ru`, `nevarium-vizor.ru`
(каждый с www), плюс `nevarium1.vercel.app`. Отдельных действий не требуется. Если
понадобится добавить ещё один (например, превью-домен) — через страницу «Настройки»
в CRM или напрямую в БД (см. `docs/DECISIONS.md`, ADR-006): без домена в списке браузер
заблокирует отправку формы (CORS), заявка не дойдёт.

Проверьте, что вход в саму CRM работает: попробуйте создать или изменить контакт.
Если `APP_ORIGIN` указан неверно (опечатка, лишний слеш на конце, http вместо https) —
любое изменение будет падать с `403 forbidden`, хотя чтение (списки, дашборд) продолжит
работать. Это ожидаемо: значение должно точь-в-точь совпадать с тем, что браузер
присылает в заголовке `Origin` — то есть `https://crm-nevarium.ru`, без пути и слеша.

Откройте `https://ваш-домен/crm` → войдите → дашборд. Отправьте тестовую заявку с
сайта — она должна появиться в «Новых лидах», и придут два уведомления (ADR-009):
в **Telegram** обезличенное, только проект, источник и ссылка на карточку; в **MAX**
полное, с именем, контактом и задачей. Так и задумано: MAX российский, туда ПДн можно,
Telegram зарубежный — туда нельзя (152-ФЗ). Если в Telegram пришло имя или телефон —
это ошибка, не выкатывайте дальше.

## Бэкапы

Защита двухуровневая, и уровни разного рода:

| Что | Кто делает | Чем возвращается |
|---|---|---|
| Снимок всей базы | **Timeweb Managed PostgreSQL**, автобэкапы (включить в настройках базы, шаг 6) | из панели Timeweb, штатным восстановлением базы |
| `crm-ГГГГ-ММ-ДД.json` | наш сервер, каждую ночь в 04:00 МСК, отправка в **MAX** | «Импорт JSON» в настройках CRM, через браузер |

JSON-дамп уходит только в MAX и никогда в Telegram: внутри ПДн всех клиентов, а
Telegram зарубежный (152-ФЗ, ADR-009). В Telegram приходит лишь обезличенный статус,
если бэкап не отправился. На диске держатся 7 последних дат.

> **Почему не файл базы.** Раньше рядом с JSON уезжала вторая копия `.sqlite`
> (`VACUUM INTO`). С переводом на Postgres она исчезла: у Postgres нет такого
> однокомандного самодостаточного снимка (`pg_dump` в контейнере приложения может
> не быть), а роль «точной копии» теперь играют автобэкапы самой Timeweb-базы.
> JSON остаётся тем, чем и был: переносимым путём восстановления через браузер,
> единственным, который работает там, где нет shell (ADR-013).

### Восстановление на App Platform (основной путь, проверено)

1. Откройте `https://crm-nevarium.ru/crm`. Если база пуста и войти не под кем —
   временно верните переменные `BOOTSTRAP_ADMIN_*` в настройках приложения,
   передеплойте, войдите, потом снимите их обратно.
2. Скачайте из чата с ботом MAX последний файл `crm-ГГГГ-ММ-ДД.json`.
3. В CRM: **Настройки → Импорт JSON** → выберите скачанный файл.
   Импорт **заменяет все данные целиком** и спрашивает подтверждение дважды.
4. Проверьте дашборд: контакты, сделки, воронка, раздел «Права ПДн».

### Восстановление из снимка базы (точный путь)

Восстановление автобэкапа Managed PostgreSQL делается в панели Timeweb, средствами
самой базы — приложение при этом трогать не нужно, оно подхватит восстановленные
данные по той же `DATABASE_URL`. Этот путь точнее JSON: возвращает в том числе
пользователей и серии воронки возврата, которых в дампе нет (см. ниже).

### Что JSON НЕ возвращает (важно знать заранее)

- **Пользователей и пароли.** После восстановления входите текущим админом или
  создайте его через `BOOTSTRAP_ADMIN_*`. Сделано намеренно: иначе чужой дамп мог бы
  подменить администратора и запереть вход.
- **Серии воронки возврата.** Задачи из них останутся с прежними заголовками и
  датами, но перестанут сниматься автоматически при возврате сделки в работу.
  Стадия «Проиграно» у сделки сохраняется, так что смысл не теряется.
- **Демо-данные.** В бэкап они не попадают вообще. Если тестируете на демо-базе,
  дамп будет выглядеть пустым — это правильное поведение, а не поломка.

Возвращается всё остальное, включая **запросы по персональным данным и журнал
действий** — то, чем доказывают Роскомнадзору исполнение обязательств в срок.

Ручной экспорт в любой момент: **Настройки → Экспорт JSON**.

## Локальная разработка

```bash
# терминал 1: API (dev-режим, cookie без Secure).
# DATABASE_URL обязателен — самодостаточного файла-базы, как было у SQLite, больше нет:
# нужен работающий Postgres (локальный или dev-база в Timeweb).
JWT_SECRET=dev-secret-dev-secret NODE_ENV=development DATABASE_URL=postgresql://user:pass@localhost:5432/nevarium_crm node server/index.js
# терминал 2: сайт (vite proxy /api → :3001 уже настроен)
npm run dev
```
