# Невариум CRM — заметки для ИИ-агента

Единая CRM для всех проектов Невариум. Владелец — не программист; поддерживает проект ИИ-агент
между сессиями. Держи контекст в `HANDOFF.md` и решения в `docs/DECISIONS.md` актуальными.

## Происхождение (важно)

Код **извлечён** из почти готовой CRM, найденной в `G:\nevarium` (старый вытесненный вариант
сайта Лаб ИИ), worktree `.claude/worktrees/nevarium-crm-design-a99bd4`. Решение — **дорабатывать,
не переписывать** (ADR-001). Оригинал `G:\nevarium` **не трогать** — только как источник.
Не путать с `G:\nvizor-app` (desktop-стройконтроль, не CRM).

## Стек и команды

- Бэкенд: Fastify + better-sqlite3 (`server/`), фронт: React + react-router + Vite (`src/crm/`).
- `node server/dev.js` — бэкенд :3001. `npm run dev` — фронт :5173 (прокси `/api`→:3001).
- `npm test` — 76 тестов (`server/api.test.js`, `src/crm/neva/parser.test.js`).
- Первый админ: `npm run seed-admin` (интерактивно, нужен shell) или переменные
  `BOOTSTRAP_ADMIN_EMAIL`/`BOOTSTRAP_ADMIN_PASSWORD` при первом старте сервера
  (`server/bootstrap.js` — для сред без shell, например App Platform; см. ADR-008).

## Архитектура

- `server/app.js` — `buildApp()`: все роуты. **Generic CRUD** через конфиг `ENTITIES`
  (contacts/deals/tasks/interactions): добавление поля в `fields` протаскивает его через
  create/list/update автоматически — этим дёшево добавляется мультипроектность.
- `server/db.js` — схема как массив миграций + `PRAGMA user_version`. Новая миграция =
  ещё одна строка в `MIGRATIONS`. Enum-стадии — в `src/shared/stages.js` (общий с фронтом).
- Публичный `POST /api/leads` — приём заявок с сайтов: honeypot (поле `website`) + rate-limit
  по IP → пометка `suspicious`, НЕ отброс (CGNAT в РФ даёт ложные срабатывания). Создаёт
  контакт + сделку в стадии «Новый». Проект: поле `project` → домен (`projects.origins`) →
  по умолчанию; заявку не отвергаем никогда (ADR-006). CORS включён только здесь, по списку
  `projects.origins` (+ localhost в dev).
- `server/telegram.js` — outbox с ретраями, **два канала: Telegram и MAX** (имя файла
  историческое). Главное правило, от которого зависит законность (152-ФЗ, ADR-009):
  **в Telegram — никогда ничего с ПДн, в MAX — можно.** Telegram зарубежный, MAX российский.
  - Telegram получает `leadMessage()`: только проект, источник, `contactId`, `suspicious` —
    никаких имён, телефонов, текста заявки. Ссылка на карточку — из `CRM_BASE_URL`.
  - MAX получает `leadMessageFull()`: имя, контакт, задачу, заметку. ПДн берутся из БД
    по `contactId` **в момент отправки** — сам `outbox.payload` остаётся обезличенным,
    чтобы ПДн не дублировались в очередь на диске.
  - Каналы независимы (миграция v7): свои `tg_*`/`max_*` колонки `sent_at`/`attempts`/
    `last_error`. Добавляя третий канал — добавляй свою тройку колонок, не переиспользуй.
  - **Ночной бэкап (`server/backup.js`) — только в MAX.** В файле базы лежат ПДн всех
    клиентов; отправка его в Telegram была бы трансграничной передачей. В Telegram уходит
    лишь обезличенный статус «сделан / не ушёл».
  - MAX требует корневой сертификат Минцифры (`server/certs/`), подключён через
    `NODE_EXTRA_CA_CERTS` в `deploy/Dockerfile` и `server/dev.js`. Без него — TLS-ошибка.
- **«Остывают»** (плитка 03 дашборда, ADR-012) — живые сделки с тишиной дольше
  `COOLING_DAYS = 3` (календарных). Отсчёт от последнего взаимодействия, а без них —
  от создания сделки. Сделки с открытой задачей и обезличенные контакты исключены;
  на этих двух исключениях держится то, что блок не шумит.
- Дашборд — ~9 агрегирующих запросов, все учитывают `?project=`. Фрагмент фильтра
  подставляется хелпером `pf(sql)`, аргументы — через `arg`; добавляя новый запрос,
  не забудь про них. Задачи и взаимодействия фильтруются через `contacts` (своего
  `project_id` у них нет); задачи без контакта — общие, видны в любом проекте.
- **Права субъекта ПДн** (`/crm/privacy`, ADR-011) — механизм, исполняющий обещание
  политики «10 рабочих дней». Запросы в `pd_requests` (приём вручную и публичным
  `POST /api/pd-requests`), срок считает `addWorkdays()` — только пн–пт, праздники
  сознательно не учитываются. `anonymizeContact()` затирает опознающие поля и тексты
  заметок, **сохраняет сделку со стадией и суммой** (иначе поедет воронка за прошлые
  периоды) и **удаляет задачи** контакта. Идемпотентно. Меняя обезличивание, помни:
  любое новое поле со свободным текстом, привязанное к контакту, надо затирать и здесь.
- **Журнал действий** — `audit()` пишет и в лог процесса, и в таблицу `audit_log`
  (логи контейнера теряются при передеплое). Читается на `/crm/privacy`, только admin.
- **Экспорт/импорт JSON — это путь восстановления, а не удобство** (ADR-013): на
  App Platform нет shell, файл базы туда не положить, поэтому «Импорт JSON» из настроек
  единственный способ вернуть данные. Дамп собирает `buildDump()` в `server/db.js`
  (список — `DUMP_TABLES`, версия формата `DUMP_VERSION`), им же пользуется ночной бэкап.
  **Добавил таблицу или колонку — допиши в `DUMP_TABLES` / `EXTRA_COLS` / `PLAIN_COLS`
  в `server/app.js`**, иначе данные не переживут восстановление, а импорт своего же
  экспорта упадёт с «bad_file». На этом уже дважды спотыкались (`winback_sequence_id`,
  `anonymized_at`). Таблицы вне дампа (`winback_sequences`) при импорте очищаются:
  их внешний ключ иначе блокирует `DELETE FROM deals`. Пользователей импорт намеренно
  не восстанавливает — чтобы чужой дамп не заменил админа и не запер вход.
- `src/main.jsx` — standalone-точка входа: монтирует `CrmApp`, корень `/` → `/crm`.
  `CrmApp` не изменялся при извлечении.
- `server/index.js` — прод-вход: собирает `staticDir` (папка `dist/` рядом с `server/`) и
  передаёт в `buildApp()`, чтобы Node сам отдавал фронт (ADR-008) — один контейнер, без
  Caddy. В тестах и dev `staticDir` не передаётся, эта ветка кода там не активируется.

## Мультипроектность (готово — Вехи 2–5)

Справочник `projects` + `project_id` на `contacts` и `deals`; задачи и взаимодействия
наследуют проект через контакт. Проекты: `nevarium1` / «Невариум Лаб ИИ», `nevarium-vizor` /
«Невариум Визор». В API: `resolveProjectId()` понимает slug и id, фильтр
`?project=<slug|id|all>`, неизвестный проект → 400.

**Осторожно с `project_id`:** колонка `NOT NULL DEFAULT 1` без внешнего ключа — так вынудил
SQLite (см. ADR-005). Значит целостность держится на приложении: любой новый путь записи
контакта или сделки обязан проставлять валидный проект, иначе заявка молча уедет в «Лаб ИИ».
Та же логика — у `tasks.winback_sequence_id` (ADR-007, воронка возврата после отказа).

**Фронтенд:** весь выбор проекта — в `src/crm/projects.jsx`. Выбор общий для всех страниц
(localStorage), список проектов кэшируется на сессию. Бейдж проекта показываем только в
режиме «Все». Списки грузим через `repo.list(entity, { q, project })` и нумеруем запросы,
чтобы медленный старый ответ не затёр свежий при переключении.

Остаток по вехам — в `HANDOFF.md`: деплой на Timeweb (ADR-008), пуш сайтов после него.

## Домашние правила

- **Не коммитить и не пушить без явной просьбы.** Владелец решает, когда «отгружаем».
- **Не редактировать без согласования** контент/поведенческие изменения — сначала показать, потом менять.
- SQLite на РФ-VPS — осознанный выбор (ADR-003), не «заменить на Postgres» без явного решения.
- Хранение ПДн — только РФ (152-ФЗ). Google Fonts в `index.html` — единственная внешняя
  зависимость, при желании самохостить.
- `data/*.sqlite` в `.gitignore` — базу не коммитить. `data/.gitkeep` держит папку (иначе
  better-sqlite3 падает: «directory does not exist»).
