# Невариум CRM — заметки для ИИ-агента

Единая CRM для всех проектов Невариум. Владелец — не программист; поддерживает проект ИИ-агент
между сессиями. Держи контекст в `HANDOFF.md` и решения в `docs/DECISIONS.md` актуальными.

## Происхождение (важно)

Код **извлечён** из почти готовой CRM, найденной в `G:\nevarium` (старый вытесненный вариант
сайта Лаб ИИ), worktree `.claude/worktrees/nevarium-crm-design-a99bd4`. Решение — **дорабатывать,
не переписывать** (ADR-001). Оригинал `G:\nevarium` **не трогать** — только как источник.
Не путать с `G:\nvizor-app` (desktop-стройконтроль, не CRM).

## Стек и команды

- Бэкенд: Fastify + `pg` (управляемый Postgres, был better-sqlite3 — перевод, ADR-003
  «заменено», план в `nevarium-lab#3`), фронт: React + react-router + Vite (`src/crm/`).
- `node server/dev.js` — бэкенд :3001 (требует `DATABASE_URL` в окружении — SQLite-файла по
  умолчанию больше нет). `npm run dev` — фронт :5173 (прокси `/api`→:3001).
- `npm test` — 195 тестов, 193 зелёных + 2 намеренно `it.skip` (`server/api.test.js`,
  `src/crm/neva/parser.test.js`) — пропущенные проверяют атомарность отката транзакции
  импорта, чего тестовый движок `pg-mem` не умеет эмулировать (см. комментарий у тестов);
  обязательны к ручному прогону на настоящем Postgres перед первым деплоем.
- Первый админ: `npm run seed-admin` (интерактивно, нужен shell) или переменные
  `BOOTSTRAP_ADMIN_EMAIL`/`BOOTSTRAP_ADMIN_PASSWORD` при первом старте сервера
  (`server/bootstrap.js` — для сред без shell, например App Platform; см. ADR-008).

## Архитектура

- `server/app.js` — `buildApp()`: все роуты. **Generic CRUD** через конфиг `ENTITIES`
  (contacts/deals/tasks/interactions): добавление поля в `fields` протаскивает его через
  create/list/update автоматически — этим дёшево добавляется мультипроектность.
- `server/db.js` — `openDb()` применяет `server/schema.sql` (одна цельная, идемпотентная
  схема — не массив миграций: перевод на Postgres убрал понятие «применить только
  недостающее», см. ADR-003) и сидирует `projects`. Новое поле/таблица = правь `schema.sql`
  напрямую. Enum-стадии — в `src/shared/stages.js` (общий с фронтом). `server/db-adapter.js` —
  тонкий асинхронный слой над `pg`, имитирующий интерфейс `.prepare(sql).get/all/run()`
  better-sqlite3 (включая именованные `@col`-параметры), чтобы сам текст SQL-запросов в
  `app.js` не пришлось переписывать — только добавить `await`. `withTransaction(pool, fn)`
  заменяет `db.transaction(fn)()`; функция, уже открывшая транзакцию, обязана передать свой
  `tx` дальше явным параметром — вложенных транзакций (SAVEPOINT) адаптер не поддерживает
  (см. `anonymizeContact`, `audit()` в `app.js` — обе принимают опциональный `tx`).
- Публичные `POST /api/leads` и `POST /api/pd-requests` — приём с сайтов, общая защита
  (ADR-015, по ТЗ `nevarium_vizor/docs/CRM-REQUIREMENTS.md`): **honeypot** (поле `website`)
  для лидов — молчаливый дроп (204/успех, НЕ сохраняет и НЕ уведомляет); для ПДн-запросов —
  НЕ дроп, только пометка `suspicious` (потерянный ПДн-запрос — просроченный законный срок
  без единого следа, цена ложного срабатывания там выше). **Мягкая IP-эвристика**
  `leadSuspicious` — пометка `suspicious`, НЕ отброс (CGNAT в РФ даёт ложные срабатывания).
  **Жёсткий порог по IP** (`hardRateLimited`, щедрый) — `429` при явном флуде с одного адреса;
  ЭТОТ `429` не сохраняет запись (сайт трактует как «повторить с тем же ключом»).
  **Глобальная квота на проект — ТОЛЬКО у `/api/leads`** (`leadNotifyBudgetOk`, час/60) —
  отдельно от per-IP: ловит распределённый всплеск с многих адресов, но **гасит только
  `enqueue()`, НЕ приём** — заявка всегда сохраняется. `/api/pd-requests` в этом механизме
  НЕ участвует вообще (ADR-015, раунды 17 и 19): ни блокировка приёма, ни даже гейт на
  уведомление — цена пропущенного пинга о ПДн-запросе (кандидат на жалобу в РКН) выше цены
  пропущенного лида (коммерческое неудобство). Не заводи квоту заново для pd-requests, если
  трогаешь этот код. При насыщении бюджета лидов сервер шлёт РОВНО ОДНО эскалационное
  уведомление на проект на окно (раунд 23) — без него исчерпание бюджета неотличимо от
  обычного затишья; не одно на каждую скрытую заявку. **Идемпотентность** — `Idempotency-Key` заголовок/`request_id` в
  теле, таблица `idempotency_keys` (миграция v9): повтор с тем же ключом не плодит вторую
  запись. **Неизвестные поля в теле** — не отказ (нарушил бы «не отвергаем никогда»), только
  `app.log.warn()` с именами ключей (не значениями). Лиды создают контакт + сделку в стадии
  «Новый». Проект: домен (`projects.origins`, доверенный `Origin`) → поле `project` (только
  запасной путь, без `Origin` не может его перекрыть) → по умолчанию; заявку не отвергаем
  никогда (ADR-006). CORS включён только здесь, по списку `projects.origins` (+ localhost в dev).
- **Слепок согласия** (`consents`, миграция v11) — `POST /api/leads` шлёт `{version, text,
  accepted_at}`, CRM сохраняет КАЖДУЮ отправку отдельной строкой (не перезаписывает: разные
  обращения одного человека могут нести разную версию политики). Юридическое доказательство
  по 152-ФЗ ст.9 (обязательна с 2026-09-01) — без него оператору нечем подтвердить согласие
  при проверке. `contact_id`/`deal_id` БЕЗ внешнего ключа (как `pd_requests.contact_id`) —
  должны пережить импорт дампа, который эту таблицу не нёс (см. `hasConsents` в
  `POST /api/crm/import`, отдельно от `hasCompliance`: тот про `pd_requests`, это про более
  новую `consents` — не путать одно с другим при добавлении следующей комплаенс-таблицы).
  `requester` (сырой контакт как прислан) — НЕЗАВИСИМАЯ от `contact_id` привязка к человеку
  (как `pd_requests.requester`): без неё legacy-импорт, обнуляя `contact_id`, оставлял бы
  согласие без единой зацепки, кому оно принадлежит (ADR-015, раунд 17) — трогая обнуление
  привязки, не забывай, что `requester` обязан остаться нетронутым, ПОКА строка не чистится.
  Само содержимое (`requester`/`version`/`text`/`accepted_at`) чистится ДВУМЯ путями — оба
  обязаны оставаться синхронными при будущих правках, и оба чистят ВСЕ четыре поля, не
  только `requester` (раунд 23: `version`/`text` — тоже attacker-controlled свободный текст
  с публичного эндпоинта, недоказуемо свободный от ПДн): `anonymizeContact` (по `contact_id`,
  плюс отдельно по значению для осиротевших импортом строк — раунд 21) оставляет строку с
  пустым содержимым; `DELETE /api/crm/contacts/:id` удаляет строку целиком (по `contact_id`
  И по значению — через общую `orphanedConsentIds()` (у `phoneKey`, ADR-015 раунд 25:
  сравнение осиротевших строк ОБЯЗАНО нормализовать телефон тем же способом, что
  `findExistingContact` — раньше два формата одного номера не совпадали как строки, и
  вторая запись переживала обезличивание). `phoneKeyIfPlausible` внутри неё (раунд 26)
  ОБЯЗАН отсекать значения с `@` от нормализации как телефон — иначе email со случайной
  10-значной цепочкой цифр совпадает с ЧУЖИМ телефоном и стирает его согласие; меняя
  это, не убирай гвард. `DELETE /api/crm/contacts/:id` теперь одной транзакцией
  (раунд 26). `DELETE /api/crm/deals/:id` — только рвёт
  `deal_id`, сама строка не трогается. `text` — потолок `CONSENT_TEXT_MAX = 20000`
  (раунд 25; было вовсе без потолка после раунда 22 — тихо позволяло ~64 КБ на запись,
  ощутимо усиливая уже принятый в раундах 17/19 остаточный риск «распределённый флуд
  растит БД без ограничения на приём»). Обрезка ВИДНА, не тиха: `consents.text_truncated`
  (раунд 27) — `1`, если реальный текст был длиннее потолка. И `anonymizeContact`, и
  `DELETE .../contacts/:id` сбрасывают её в `0` вместе с остальным содержимым — не
  забудь про это при следующей правке очистки. `warnUnknownFields` (у `LEAD_FIELDS`) —
  вызывается ПОСЛЕ `hardRateLimited` в обоих публичных обработчиках, не до (раунд 27:
  уже заблокированный по IP не должен продолжать генерировать лог-записи), и сама режет
  число/длину имён полей — не убирай эти пределы, добавляя новый вызов.
- **Дубли на приёме** (`findExistingContact`, ADR-014): тот же человек не заводит вторую
  карточку. Совпадение строго по контакту (почта/телефон/ник, телефон нормализуется
  через `phoneKey`), **по имени не ищем** — склеить разных клиентов хуже, чем две карточки.
  Ищем внутри проекта и мимо обезличенных. При совпадении: открытая сделка
  переиспользуется (иначе воронка считает возможность дважды), закрытая → заводится новая,
  контакт возвращается из архива, активная воронка возврата отменяется, текст обращения
  уходит в `interactions`. Меняя это — помни, что склейку правят сменой контакта у сделки.
- `server/telegram.js` — outbox с ретраями, **два канала: Telegram и MAX** (имя файла
  историческое). Главное правило, от которого зависит законность (152-ФЗ, ADR-009):
  **в Telegram — никогда ничего с ПДн, в MAX — можно.** Telegram зарубежный, MAX российский.
  - Telegram получает `leadMessage()`: только проект, источник, `contactId`, `suspicious` —
    никаких имён, телефонов, текста заявки. Ссылка на карточку — из `CRM_BASE_URL`.
  - MAX получает `leadMessageFull()`: имя, контакт, задачу, заметку. ПДн берутся из БД
    по `contactId` **в момент отправки** — сам `outbox.payload` остаётся обезличенным,
    чтобы ПДн не дублировались в очередь на диске.
  - Каналы независимы (миграция v7): свои `tg_*`/`max_*` колонки `sent_at`/`attempts`/
    `last_error`. Добавляя третий канал — добавляй свою тройку колонок, не переиспользуй.
  - **Ночной бэкап (`server/backup.js`) — только в MAX.** В файле базы лежат ПДн всех
    клиентов; отправка его в Telegram была бы трансграничной передачей. В Telegram уходит
    лишь обезличенный статус «сделан / не ушёл».
  - MAX требует корневой сертификат Минцифры (`server/certs/`), подключён через
    `NODE_EXTRA_CA_CERTS` в `deploy/Dockerfile` и `server/dev.js`. Без него — TLS-ошибка.
- **«Остывают»** (плитка 03 дашборда, ADR-012) — живые сделки с тишиной дольше
  `COOLING_DAYS = 3` (календарных). Отсчёт от последнего взаимодействия, а без них —
  от создания сделки. Сделки с открытой задачей и обезличенные контакты исключены;
  на этих двух исключениях держится то, что блок не шумит.
- Дашборд — ~9 агрегирующих запросов, все учитывают `?project=`. Фрагмент фильтра
  подставляется хелпером `pf(sql)`, аргументы — через `arg`; добавляя новый запрос,
  не забудь про них. Задачи и взаимодействия фильтруются через `contacts` (своего
  `project_id` у них нет); задачи без контакта — общие, видны в любом проекте.
- **Права субъекта ПДн** (`/crm/privacy`, ADR-011, ADR-015) — механизм, исполняющий обещание
  политики «10 рабочих дней». Запросы в `pd_requests` (приём вручную → статус `new`, публичным
  `POST /api/pd-requests` → статус **`pending_unverified`**: веб-форма не подтверждает личность
  отправителя, атакующий может знать чужой email/телефон). Пока статус `pending_unverified`,
  сервер блокирует и `PATCH .../anonymize`, и прямой переход в `status: 'done'` (`400
  not_verified`) — сотрудник обязан явно подтвердить личность по контакту ИЗ КАРТОЧКИ (не из
  формы) и перевести статус дальше. Срок считает `addWorkdays()` — только пн–пт, праздники
  сознательно не учитываются. `anonymizeContact()` затирает опознающие поля и тексты
  заметок (включая `consents.requester` — независимая проверка, ADR-015 раунд 20, поймала,
  что новую таблицу с ПДн-полем сюда не добавили при её же появлении), **сохраняет сделку
  со стадией и суммой** (иначе поедет воронка за прошлые периоды) и **удаляет задачи**
  контакта. Идемпотентно. Меняя обезличивание, помни: любое новое поле со свободным
  текстом ИЛИ контактом (email/телефон/ник), привязанное к contact_id где бы то ни было —
  не только в `contacts`/`interactions`/`deals` — надо затирать и здесь. Это уже забывали
  при добавлении новой таблицы (`consents`) в этой самой сессии — не единичный риск.
- **Журнал действий** — `audit()` пишет и в лог процесса, и в таблицу `audit_log`
  (логи контейнера теряются при передеплое). Читается на `/crm/privacy`, только admin.
- **Экспорт/импорт JSON — это путь восстановления, а не удобство** (ADR-013): на
  App Platform нет shell, файл базы туда не положить, поэтому «Импорт JSON» из настроек
  единственный способ вернуть данные. Дамп собирает `buildDump()` в `server/db.js`
  (список — `DUMP_TABLES`, версия формата `DUMP_VERSION`), им же пользуется ночной бэкап.
  **Добавил таблицу или колонку — допиши в `DUMP_TABLES` / `EXTRA_COLS` / `PLAIN_COLS`
  в `server/app.js`**, иначе данные не переживут восстановление, а импорт своего же
  экспорта упадёт с «bad_file». На этом уже дважды спотыкались (`winback_sequence_id`,
  `anonymized_at`). Таблицы вне дампа (`winback_sequences`) при импорте очищаются:
  их внешний ключ иначе блокирует `DELETE FROM deals`. Пользователей импорт намеренно
  не восстанавливает — чтобы чужой дамп не заменил админа и не запер вход.
- `src/main.jsx` — standalone-точка входа: монтирует `CrmApp`, корень `/` → `/crm`.
  `CrmApp` не изменялся при извлечении.
- `server/index.js` — прод-вход: собирает `staticDir` (папка `dist/` рядом с `server/`) и
  передаёт в `buildApp()`, чтобы Node сам отдавал фронт (ADR-008) — один контейнер, без
  Caddy. В тестах и dev `staticDir` не передаётся, эта ветка кода там не активируется.

## Мультипроектность (готово — Вехи 2–5)

Справочник `projects` + `project_id` на `contacts` и `deals`; задачи и взаимодействия
наследуют проект через контакт. Проекты: `nevarium1` / «Невариум Лаб ИИ», `nevarium-vizor` /
«Невариум Визор». В API: `resolveProjectId()` понимает slug и id, фильтр
`?project=<slug|id|all>`, неизвестный проект → 400.

**`project_id`:** `NOT NULL DEFAULT 1`, и в `schema.sql` (Postgres) — уже С настоящим
`REFERENCES projects(id)` (было без FK при SQLite, см. историю решения в ADR-005 — то было
ограничение платформы, ALTER TABLE ADD COLUMN с REFERENCES и ненулевым дефолтом SQLite не
разрешал, не архитектурное решение; перевод на Postgres, ADR-003, эту обходку убрал). Дефолт
на 1 всё ещё держит гарантию «у каждой заявки есть проект» приложением, а не только FK: любой
новый путь записи контакта/сделки обязан проставлять валидный проект, иначе заявка молча
уедет в «Лаб ИИ». Та же логика и та же смена (был без FK → теперь с FK) — у
`tasks.winback_sequence_id` (ADR-007, воронка возврата после отказа).

**Фронтенд:** весь выбор проекта — в `src/crm/projects.jsx`. Выбор общий для всех страниц
(localStorage), список проектов кэшируется на сессию. Бейдж проекта показываем только в
режиме «Все». Списки грузим через `repo.list(entity, { q, project })` и нумеруем запросы,
чтобы медленный старый ответ не затёр свежий при переключении.

Остаток по вехам — в `HANDOFF.md`: деплой на Timeweb (ADR-008), пуш сайтов после него.

## Домашние правила

- **Не коммитить и не пушить без явной просьбы.** Владелец решает, когда «отгружаем».
- **Не редактировать без согласования** контент/поведенческие изменения — сначала показать, потом менять.
- **ADR-003 «заменено»**: SQLite на РФ-VPS был осознанным выбором, но переведён на управляемый
  Postgres (Timeweb) — App Platform не сохраняет файлы контейнера между деплоями, SQLite-файл
  терял бы все заявки при каждом обновлении. План перевода и его обоснование —
  `nevarium-spb/nevarium-lab#3` (`docs/CRM_POSTGRES_MIGRATION_SPEC.md` в той ветке). Подробности
  перевода (что изменилось в коде, чего pg-mem не умеет для тестов) — раздел выше в
  «Стек и команды»/«Архитектура» и `HANDOFF.md`.
- Хранение ПДн — только РФ (152-ФЗ), в т.ч. управляемый Postgres — только у российского
  провайдера (Timeweb). Google Fonts в `index.html` — единственная внешняя зависимость,
  при желании самохостить.
- `data/backups/` — JSON-бэкапы (`server/backup.js`), не коммитить (в `.gitignore`).
  Самой базы в файле больше нет (Postgres, не SQLite) — `data/*.sqlite`/`data/.gitkeep` были
  нужны только под неё, актуальности для БД не имеют.
